# Восстановление пароля — 30.09.2026

## Согласовано

- Только для восстановления: одинаковое сообщение для существующей и неизвестной почты — «Если аккаунт с этой почтой существует, мы отправили код. Не получили письмо? Проверьте адрес и папку „Спам“».
- Не создавать аккаунт и не выдавать факт регистрации почты. До правильного кода не открывать новый пароль.
- Без CAPTCHA пока; ограничения Supabase сохраняются. Повторная отправка через 60 секунд, можно исправить адрес.
- Код восстановления не заменяет постоянный пароль. Изменение только после проверки recovery-кода и сохранения нового пароля с повтором.
- Нейтральное сообщение не распространяется этим решением на регистрацию. Подтверждение обычной регистрации кодом реализовано отдельно в `SignupConfirmationForm` и опубликовано.

## Реализовано и опубликовано

- `src/components/auth/PasswordRecoveryForm.tsx` используется в AuthPage и RequestInvitePage.
- Запрос `resetPasswordForEmail` (`/recover`), не `signInWithOtp` (`/otp`). Неизвестный адрес не создаёт пользователя. UI не вызывает поиск пользователя по email.
- Проверка `verifyOtp(type: recovery)` отдельным Auth-клиентом с persistSession/autoRefreshToken/detectSessionInUrl=false. Не вызывает автоматический вход основного приложения до изменения пароля.
- Пароль валидируется и нормализуется по существующим правилам проекта. После успешного updateUser запрашивается global signOut, отображается приглашение войти заново.
- `supabase/templates/recovery.html`: только код, без ConfirmationURL. Live-шаблон обновлён после успешной публикации нового UI. Старый ResetPasswordPage оставлен для уже отправленных ссылок. Проверка полного сценария реальным письмом остаётся за пользователем.
- `npm run build`, `tests/password-recovery.browser.mjs`, `tests/request-workflow.browser.mjs` прошли. API в браузерных тестах полностью подменён; реальным пользователям письма не отправлялись и их пароли не менялись.

## Обычная регистрация и клиентская ссылка

- После успешного signUp показывается форма signup-кода, пароль/повтор очищаются из React state. До verifyOtp с type=signup основной Auth-сессии нет.
- При попытке входа с неподтверждённой почтой (email_not_confirmed) открывается та же форма; пользователь может ввести прежний код либо запросить новый. Повторный signUp не нужен.
- Resend signup-кода: auth.resend(type=signup), таймер 60 секунд; ошибочный/истёкший код не открывает систему. Есть возврат к изменению адреса/входу. Изменение адреса не переносит прежний неподтверждённый аккаунт: новая регистрация идёт для введённой почты.
- По клиентской ссылке остаётся email-OTP, затем создание пароля того же аккаунта; добавлен таймер повторной отправки и возврат назад. Сохранение пароля использует существующую normalizePassword, как основной вход/регистрация.
- `tests/signup-confirmation.browser.mjs` прошёл с реальным useAuth и подменёнными API: signup, неверный код, cooldown/resend, перезагрузка/вход до подтверждения, верный код и Auth-сессия.
