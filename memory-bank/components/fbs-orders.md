# FBS Orders — актуальная архитектура (11.08.2026)

## Файлы
- UI: `src/pages/FbsOrdersPage.tsx`
- Статичная справка владельца сервиса: `src/pages/FbsInfoPage.tsx`
- Edge Function: `supabase/functions/wb-fbs/index.ts`
- Миграция/RPC: `supabase/patch_fbs_reliable_sync.sql`
- Кэш: `fbs_orders`, `fbs_sync_log`
- Товары: `products`
- WMS: `wms_warehouses`, `wms_cell_items`
- Поиск товара: `fulfillment_box_items` → `fulfillment_boxes` → `fulfillment_supplies` → `fulfillment_batches`; RPC `get_fbs_product_locations`.

## Надёжный снимок WB
1. UI сразу читает последний корректный снимок из `fbs_orders`.
2. `sync_orders` загружает `/api/v3/orders` за 30 дней постранично до точного `next=0` и объединяет результат с `/api/v3/orders/new`.
3. Для каждого уникального order ID запрашивается официальная пара статусов через `/api/v3/orders/status`, батчами максимум по 1000.
4. ID и cursor, которые WB описывает как int64, разбираются и передаются как точные строки, без JS-округления.
5. RPC `apply_fbs_sync_snapshot` проверяет количество заказов/статусов и применяет весь снимок одной транзакцией.
6. При сбое новый снимок не применяется. В `fbs_sync_log.error` записывается причина, а UI продолжает показывать последний успешный снимок и время его получения.
7. Одновременные sync одного магазина объединяются; более старый снимок не может перезаписать более новый.

## Поля БД
`fbs_orders`:
- `wb_order_id text`;
- `supplier_status text`;
- `wb_system_status text`;
- `status_synced_at timestamptz`;
- `is_in_latest_snapshot boolean`.

`fbs_sync_log`:
- `last_synced_at`;
- `orders_count`;
- `status_counts jsonb`;
- `snapshot_from`;
- `error`.

## Вкладки
- В верхней панели системный владелец (`platform_role=superadmin`) видит `FBS Заказы | Инфо`; остальные роли видят обычный заголовок без вкладок. Справочная страница не монтирует `FbsOrdersPage` и не выполняет запросы заказов WB.
- `pending` / «Новые»: `supplierStatus=new`, `wbStatus=waiting`.
- `assembling` / «На сборке»: `supplierStatus=confirm`, `wbStatus=waiting`.
- `delivering` / «В доставке»: `supplierStatus=complete`, пока `wbStatus` не финальный.
- `completed` / «Завершённые»: `sold`, `canceled_by_client`, `defect`.
- `cancelled` / «Отменённые»: `supplierStatus=cancel`, `declined_by_client`, `canceled`.
- `archive` / «Архив»: строка вне последнего 30-дневного снимка либо новая неизвестная комбинация, которую нельзя безопасно отнести к другой вкладке.

Наша система не отменяет заказы. Она только читает и отображает статусы WB. `localStorage` хранит лишь UI-настройки магазина и вкладки.

## «На сборке»
- Родители формируются из всех открытых WB-поставок, поэтому пустая поставка тоже видна.
- Заказы связываются по `supply_id`; отсутствующая связь попадает в «Без поставки».
- Перенос заказа доступен в существующую или новую поставку; исходная поставка исключается из списка назначения.
- Кнопка принтера в строке заказа и печать выбранных заказов открывают одинаковую модалку выбора.
- Для одного/выбранных заказов доступны четыре типа: информация о товаре, отдельный адрес товара, товарный штрихкод и официальный WB-стикер.
- Кнопка принтера родительской поставки расположена слева от передачи в доставку и добавляет четвёртый тип — данные поставки.
- Комплект группируется по точному варианту `sku + chrtId + nmId`: одна информационная карточка варианта, затем товарный штрихкод и WB-стикер каждого заказа этого варианта.
- Все страницы имеют размер `58×40 мм`; информационные страницы рисуются локально через canvas для корректной кириллицы, официальный WB PNG вставляется без изменений.
- WB-стикеры запрашиваются пакетами максимум 100 заказов и сопоставляются с заказами по `orderId`. Неполный ответ WB блокирует выдачу PDF.
- `warehouseId` заказа указывает на склад продавца, а `officeId` — на привязанный официальный пункт приёмки FBS WB. Колонка склада показывает официальный пункт первым и имя склада продавца вторым; справочники `/api/v3/warehouses` и `/api/v3/offices` загружаются параллельно одним действием Edge Function.
- Массовая нижняя панель содержит печать, перенос, лист подбора и сброс выбора. Передачи отдельных заказов в доставку нет.

## Передача в доставку
- Действие доступно только на родителе поставки.
- Сначала вызывается официальный `PATCH /api/v3/supplies/{supplyId}/deliver`.
- Затем обновляются связанные WMS-остатки и запускается полный sync; вкладка определяется новым статусом WB, а не локальной подстановкой.

## Данные товара
- FBS WB order — источник `order id`, `nmId`, `chrtId`, `skus`.
- Баркод берётся из `skus` конкретного заказа.
- `products` по `store_id + nm_id` даёт фото, название, бренд и артикул продавца.
- Размер ищется в `products.sizes` по точному SKU и `chrtId`; случайный размер не подставляется.
- Нет точного варианта — UI показывает «Размер не определён» и предлагает синхронизацию товаров.

## Адрес товара и короба
- Все уникальные баркоды страницы передаются одним запросом в `get_fbs_product_locations`; отдельных запросов на каждую строку нет.
- Баркод товара ищется в `fulfillment_box_items.barcode`, а не в `wms_cell_items.barcode`, где хранится ШК физического короба.
- Для каждого совпадения возвращаются партия `P-N`, поставка `S-N`, короб, количество и текущее WMS-размещение.
- Размещённый короб показывает полный адрес `Склад · Стеллаж · Сторона · B3-K5`.
- Неразмещённый короб показывает `Без адреса`, но сохраняет видимые партию, поставку, короб и количество.
- Несколько коробов одного товара не схлопываются: первые два видны сразу, остальные раскрываются через `Ещё N коробов`.
- `Не найден` показывается только если баркод отсутствует во всех актуальных коробах компании. Отменённые партии и уже отгруженные поставки исключаются.
- Это read-only поиск: открытие FBS и передача WB-поставки в доставку не изменяют содержимое WMS-коробов.
- SQL: `supabase/patch_fbs_product_locations.sql`; применён в production 16.08.2026.
