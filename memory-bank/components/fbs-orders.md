# FBS Orders — актуальная архитектура (11.08.2026)

## Файлы
- UI: `src/pages/FbsOrdersPage.tsx`
- Статичная справка владельца сервиса: `src/pages/FbsInfoPage.tsx`
- Edge Function: `supabase/functions/wb-fbs/index.ts`
- Миграция/RPC: `supabase/patch_fbs_reliable_sync.sql`
- Кэш: `fbs_orders`, `fbs_sync_log`
- Товары: `products`
- WMS: `wms_warehouses`, `wms_cell_items`
- Поиск товара: `fulfillment_box_items` → `fulfillment_boxes` → `fulfillment_supplies` → `fulfillment_batches`; RPC `get_fbs_product_locations`.

## Надёжный снимок WB
1. UI сразу читает последний корректный снимок из `fbs_orders`.
2. `sync_orders` загружает `/api/v3/orders` за 30 дней постранично до точного `next=0` и объединяет результат с `/api/v3/orders/new`.
3. Для каждого уникального order ID запрашивается официальная пара статусов через `/api/v3/orders/status`, батчами максимум по 1000.
4. ID и cursor, которые WB описывает как int64, разбираются и передаются как точные строки, без JS-округления.
5. RPC `apply_fbs_sync_snapshot` проверяет количество заказов/статусов и применяет весь снимок одной транзакцией.
6. При сбое новый снимок не применяется. В `fbs_sync_log.error` записывается причина, а UI продолжает показывать последний успешный снимок и время его получения.
7. Одновременные sync одного магазина объединяются; более старый снимок не может перезаписать более новый.

## Поля БД
`fbs_orders`:
- `wb_order_id text`;
- `supplier_status text`;
- `wb_system_status text`;
- `status_synced_at timestamptz`;
- `is_in_latest_snapshot boolean`.

`fbs_sync_log`:
- `last_synced_at`;
- `orders_count`;
- `status_counts jsonb`;
- `snapshot_from`;
- `error`.

## Фильтр склада

- В верхней панели после выбора WB-магазина находится фильтр склада; первым вариантом всегда идёт `Все склады`.
- Каждый вариант показывает оба имени в порядке `Наш склад — Склад WB: официальный пункт`, например `Ак логистик — Склад WB: Москва (Белая дача)`.
- Значение фильтра — точный `warehouseId` заказа. Пользовательское имя берётся из справочника складов WB и, при наличии связи `wms_warehouses.wb_warehouse_id`, уточняется внутренним названием WMS; официальный пункт определяется через `officeId`.
- Фильтр применяется к заказам до построения таблицы и групп поставок, поэтому работает в плоских и сгруппированных режимах. При выбранном складе родительская поставка без подходящих заказов полностью скрывается.
- Бейджи вкладок вычисляются по полному массиву заказов и не меняются от фильтра. Экспорт завершённых заказов и новый архивный отчёт используют текущий отфильтрованный состав.
- Выбор хранится только в браузере отдельно для каждого магазина: `fbs_warehouse_filter_{accountId}_{storeId}`. Если сохранённого `warehouseId` больше нет в актуальном справочнике магазина, автоматически включается `Все склады`.

## Вкладки
- В верхней панели системный владелец (`platform_role=superadmin`) видит `FBS Заказы | Инфо`; остальные роли видят обычный заголовок без вкладок. Справочная страница не монтирует `FbsOrdersPage` и не выполняет запросы заказов WB.
- `pending` / «Новые»: `supplierStatus=new`, `wbStatus=waiting`.
- `assembling` / «На сборке»: `supplierStatus=confirm`, `wbStatus=waiting`.
- `delivering` / «В доставке»: `supplierStatus=complete`, пока `wbStatus` не финальный.
- Список «В доставке» содержит все такие незавершённые заказы, но бейдж вкладки повторяет отдельное правило WB: считает только актуальные `supplierStatus=complete + wbStatus=waiting`, то есть переданные продавцом, но ещё не принятые WB.
- `completed` / «Завершённые»: финальная история `sold`, `canceled_by_client`, `declined_by_client`, `defect`, `canceled` и `supplierStatus=cancel` за последние 3 месяца.
- `cancelled` / «Отменённые»: только актуальная ранняя отмена покупателя `declined_by_client`.
- `archive` / «Архив»: не список строк по техническому признаку снимка, а генератор отчётов по сохранённым финальным заказам старше 3 месяцев.

Наша система не отменяет заказы. Она только читает и отображает статусы WB. `localStorage` хранит лишь UI-настройки магазина и вкладки.

## «На сборке»
- Родители формируются из всех открытых WB-поставок, поэтому пустая поставка тоже видна.
- У родительских поставок есть собственные чекбоксы и общий выбор всех родителей. Этот выбор независим от чекбоксов дочерних заказов и не отмечает товары внутри.
- Заказы связываются по `supply_id`; отсутствующая связь попадает в «Без поставки».
- Перенос заказа доступен в существующую или новую поставку; исходная поставка исключается из списка назначения.
- Кнопка принтера в строке заказа и печать выбранных заказов открывают одинаковую модалку выбора.
- Для одного/выбранных заказов доступны четыре типа: информация о товаре, отдельный адрес товара, товарный штрихкод и официальный WB-стикер.
- Кнопка принтера родительской поставки расположена слева от передачи в доставку и добавляет четвёртый тип — данные поставки.
- Комплект группируется по точному варианту `sku + chrtId + nmId`: одна информационная карточка варианта, затем товарный штрихкод и WB-стикер каждого заказа этого варианта.
- Все страницы имеют размер `58×40 мм`; информационные страницы рисуются локально через canvas для корректной кириллицы, официальный WB PNG вставляется без изменений.
- WB-стикеры запрашиваются пакетами максимум 100 заказов и сопоставляются с заказами по `orderId`. Неполный ответ WB блокирует выдачу PDF.
- `warehouseId` заказа указывает на склад продавца, а `officeId` — на привязанный официальный пункт приёмки FBS WB. Колонка склада показывает официальный пункт первым и имя склада продавца вторым; справочники `/api/v3/warehouses` и `/api/v3/offices` загружаются параллельно одним действием Edge Function.
- Массовая нижняя панель содержит печать, перенос, лист подбора и сброс выбора. Передачи отдельных заказов в доставку нет.

## «В доставке»

- Внутри раскрытой поставки у каждого заказа показывается отдельная колонка «Статус WB» из сохранённого `wb_system_status`: «Ожидает приёмки WB», «Отсортирован», «Ждёт покупателя», статусы перевозчика и переноса доставки. Новые неизвестные значения не скрываются и выводятся с исходным кодом.
- Колонка не создаёт запрос на каждую строку: статусы уже получаются пакетами до 1000 ID через официальный `POST /api/v3/orders/status` во время общей синхронизации и сохраняются в `fbs_orders`.
- Заказы отображаются не плоским списком, а дочерними строками внутри родительских WB-поставок, как на вкладке «На сборке».
- Родительские поставки имеют отдельные чекбоксы и общий выбор всех поставок; выбор заказа внутри переключает интерфейс обратно на уровень заказов.
- Названия родителей подгружаются из закрытых поставок `GET /api/v3/supplies?isSupplyClosed=true`; если WB не вернул метаданные, остаётся точный `WB-GI-…` из заказа.
- В родителе показаны название, ID, количество заказов и склад; поставку можно раскрыть и распечатать её комплект стикеров.
- Повторной кнопки передачи в доставку и переноса заказов между поставками нет: закрытую поставку WB изменять нельзя.
- Бейдж вкладки считает только `complete + waiting`, тогда как внутри родителей остаются все незавершённые `complete`-заказы.

## «Завершённые»
- По умолчанию отображается плоский список заказов с текстовым финальным статусом вместо неинформативной галочки.
- Переключатель «Сгруппировать по поставкам» включает общий с «На сборке» и «В доставке» аккордеон: поставка является родителем, заказы — дочерними строками.
- Чекбоксы поставок и вложенных заказов независимы, общий чекбокс выбирает только поставки.
- Финальные отмены входят и в «Завершённые» как историю результата, и в «Отменённые» как отдельную категорию причины.
- Кнопка «Выгрузить в Excel» экспортирует завершённые заказы; печать рабочих WB-стикеров в финальной истории не показывается.

## «Отменённые»
- Плоский оперативный список только для `is_in_latest_snapshot=true + wb_system_status=declined_by_client`.
- Поставки, группировка, чекбоксы массовых действий и печать стикеров не показываются.
- Строка получает явный статус «Отменено покупателем»; она может одновременно присутствовать в «Завершённых» как часть финальной истории.

## «Архив»
- Старые/неизвестные строки больше не выводятся как архив только из-за `is_in_latest_snapshot=false`.
- Архивными для отчёта считаются сохранённые финальные заказы старше 3 месяцев.
- `fbs_archive_reports` хранит магазин, период, количество и точный массив `order_ids`, дату создания и `expires_at`.
- XLSX формируется локально по зафиксированным ID; отчёт доступен 7 дней, удаляется пользователем или очищается при следующем входе в архив.
- Лимит 100 активных отчётов на магазин проверяется интерфейсом и DB-trigger.
- Поскольку Marketplace API отдаёт ограниченную историю, архив охватывает данные, которые сервис успел сохранить после подключения магазина.

## Передача в доставку
- Действие доступно только на родителе поставки.
- Сначала вызывается официальный `PATCH /api/v3/supplies/{supplyId}/deliver`.
- Затем обновляются связанные WMS-остатки и запускается полный sync; вкладка определяется новым статусом WB, а не локальной подстановкой.

## Быстрое сканирование КИЗ
- Над текущей инструкцией сканера расположен динамический горизонтальный прогресс `Короб → Баркод товара → QR заказа WB → КИЗ`. Отключённые опциональные проверки плавно исчезают из цепочки, а оставшиеся этапы перестраиваются с короткой CSS-анимацией. Пройденные этапы зелёные с галочкой, текущий насыщенно-синий, будущие светло-синие с номером; под каждым кругом есть подпись.
- Модальное окно сканирования занимает весь viewport приложения; шапка остаётся сверху, а весь доступный остаток экрана отдан прокручиваемому рабочему содержимому.
- Дублирующие тексты `Шаг N из N` и `Сканируйте …` над переключателями скрыты: текущий этап виден по прогрессу и placeholder поля сканирования.
- Ошибки сканирования всегда привязаны к активному этапу. Известный стикер другого типа называется прямо (`QR заказа WB`, `QR короба`, `баркод товара`), после чего сообщение сообщает, какой код требуется сейчас. Повреждённый ответ RPC заменяется этапным объяснением, а не общим `Не удалось выполнить действие`.
- Каждый этап строго принимает только свой тип данных и повторно проверяется в production RPC: короб — точный barcode существующего неотгруженного короба аккаунта; товар — SKU активного FBS-заказа с доступным официальным QR; заказ — только значение из `fbs_wb_qr_catalog`; КИЗ — валидный GS1 DataMatrix `01 + GTIN-14 + 21 + serial` с контрольной цифрой и совпадением GTIN с товаром заказа.
- Нормализация КИЗ поддерживает реальные варианты сканеров: AIM-префикс `]d2`, форму `(01)…(21)…`, ASCII GS (`0x1D`) и криптографические AI-хвосты. Случайная строка длиной 16–135 больше не считается КИЗ.
- Рабочая последовательность строго чередуется: официальный QR заказа WB → один КИЗ → следующий QR WB. Предварительно выбирать поставку или заказ не нужно; одна сессия может обработать заказы из разных открытых поставок одного магазина.
- Один заказ поддерживает один КИЗ. Заказы, для которых WB не вернул `sgtin` в `requiredMeta` или `optionalMeta`, сканер не принимает.
- Официальное соответствие QR заказу загружается Edge Function из `/api/v3/orders/stickers` и сохраняется в `fbs_wb_qr_catalog`. Поэтому во время рабочего цикла браузер не обращается к WB на каждый скан.
- `fbs_marking_sessions` хранит отдельную сессию для сочетания магазин + авторизованный пользователь + постоянный `device_id` браузера. Несколько устройств под одним аккаунтом и разные аккаунты работают независимо.
- `fbs_marking_pairs` хранит готовую пару сразу после второго скана. Уникальные индексы `(store_id, order_id)`, `(store_id, wb_qr)` и `(store_id, sgtin)` защищают от повторов между всеми устройствами магазина.
- Незавершённый QR хранится в сессии с арендой 2 минуты. Heartbeat продлевает её каждые 30 секунд; после гибели устройства заказ автоматически перестаёт блокировать других.
- Сохранённые пары погибшего устройства не освобождаются и не теряются. После 2 минут отсутствия связи другая активная сессия магазина может атомарно забрать его черновые/ошибочные пары; автор исходных сканов сохраняется в журнале.
- Realtime не участвует в критическом пути скана: он только обновляет экраны. Каждая пара создаётся одной DB-RPC транзакцией, поэтому обновление страницы безопасно.
- `Завершить и отправить в WB` обрабатывает только текущую сессию устройства. Перед PUT `/api/v3/orders/{orderId}/meta/sgtin` сервер заново проверяет официальный статус и уже записанные метаданные WB.
- Частичный ответ обрабатывается по каждой паре: успешные получают `sent`, ошибки — `error` с причиной. Повторная отправка не дублирует уже принятые пары и распознаёт идемпотентный случай, когда тот же КИЗ уже находится в WB.
- SQL: `supabase/patch_fbs_marking_scanner.sql`; сервер: действия `get_scan_catalog` и `submit_marking_session` в `supabase/functions/wb-fbs/index.ts`.

## Данные товара
- FBS WB order — источник `order id`, `nmId`, `chrtId`, `skus`.
- Баркод берётся из `skus` конкретного заказа.
- `products` по `store_id + nm_id` даёт фото, название, бренд и артикул продавца.
- Размер ищется в `products.sizes` по точному SKU и `chrtId`; случайный размер не подставляется.
- Нет точного варианта — UI показывает «Размер не определён» и предлагает синхронизацию товаров.

## Адрес товара и короба
- Все уникальные баркоды страницы передаются одним запросом в `get_fbs_product_locations`; отдельных запросов на каждую строку нет.
- Баркод товара ищется в `fulfillment_box_items.barcode`, а не в `wms_cell_items.barcode`, где хранится ШК физического короба.
- Для каждого совпадения возвращаются партия `P-N`, поставка `S-N`, короб, количество и текущее WMS-размещение.
- Размещённый короб показывает полный адрес `Склад · Стеллаж · Сторона · B3-K5`.
- Неразмещённый короб показывает `Без адреса`, но сохраняет видимые партию, поставку, короб и количество.
- Несколько коробов одного товара не схлопываются: первые два видны сразу, остальные раскрываются через `Ещё N коробов`.
- `Не найден` показывается только если баркод отсутствует во всех актуальных коробах компании. Отменённые партии и уже отгруженные поставки исключаются.
- Это read-only поиск: открытие FBS и передача WB-поставки в доставку не изменяют содержимое WMS-коробов.
- SQL: `supabase/patch_fbs_product_locations.sql`; применён в production 16.08.2026.
