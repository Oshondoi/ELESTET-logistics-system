## PREVIOUS FOCUS — 11.08.2026: адресация WMS-стеллажей

### Принятая модель
- В текущем WMS зона является целым стеллажом: `Склад → Стеллаж/зона → Паллетоместо B3 → Сторона F1/F2 → Место K5 → Короб с QR → Товар`.
- Столбцы A–Z — паллетоместа по ширине, строки 1–N — ярусы. Вертикальная стойка не является ячейкой и хранится как граница после конкретного столбца.
- Пользователь может расставить стойки через одинаковый интервал либо вручную с разным расстоянием.
- У стеллажа одна или две именованные стороны — третья запрещена и UI, и БД. Для каждой стороны отдельно настраиваются ширина и высота коробочных мест.
- Default для новых стеллажей: 3 яруса; стороны `Сторона 1` и `Сторона 2`, каждая `2×4 = 8` мест. Нумерация идёт слева направо, затем сверху вниз: `K1 K2 / K3 K4 / K5 K6 / K7 K8`.

### Реализация и защита данных
- `wms_zones`: `upright_mode`, `upright_every`, `upright_after_cols`.
- `wms_zone_sides`: стабильный код стороны, пользовательское имя, `slot_columns`, `slot_rows`, производный `slot_count`, порядок.
- `wms_cell_items`: `side_id + slot_number` для физического короба; один слот принимает только один короб, непустой ШК короба уникален в компании.
- Новый короб всегда создаётся как одна физическая единица с обязательным ШК/QR и адресом. QR визуализируется из того же строкового кода.
- Старые короба не удалены и не переделаны: у них `side_id/slot_number = null`, UI показывает «Место не назначено» и позволяет назначить адрес вручную.
- БД блокирует уменьшение сетки поверх существующих паллетомест, уменьшение `slot_count` поверх занятых K-мест, удаление используемой стороны и конфликт двух коробов в одном месте.
- Настройки стеллажа сохраняются атомарным RPC `save_wms_zone_layout`.
- Занятый короб выбирается прямо в визуальной сетке. Следующий клик переносит его в свободное место либо атомарно обменивает с занятым через `move_or_swap_wms_box`; ШК, QR и содержимое не меняются.
- SQL `supabase/patch_wms_rack_layout.sql` и `supabase/patch_wms_side_codes_f.sql` применены к production Supabase. Существующие стороны мигрированы на `F1/F2` без смены UUID: проверено 53 размещённых короба и 0 потерянных связей. Связанные WMS-функции формируют новые адреса с `F`, а сканер сохраняет совместимость со старыми кодами `S1/S2`. Все 2212 fulfillment-коробов сохранили отдельный формат поставки с `S`.

  ```ts
  const partnerBatchPipelineMap = useMemo(() => {
    const map = new Map<string, {id,name,status,order}[]>()
    for (const pb of partnerBatches) {
      const arr = map.get(pb.batch_id) ?? []
      arr.push({ id: pb.my_stage_id, name: pb.my_stage_name, status: pb.my_stage_status, order: pb.my_stage_order })
      map.set(pb.batch_id, arr)
    }
  ```

#### Pedant.kg — что это
- URL: `pedant.kg` — платный UI поверх Teksher
- Два аккаунта (компании): ОсОО АЭРОН + Ашимов Кадырали
- Интеграция Teksher стоит: 4 000 сом/мес
- Нет своего API (был `/ru/api` → 404)

#### Полный цикл маркировки
```
1. Регистрация карточки товара (один раз)
   → Teksher присваивает GTIN-14 каждому (артикул + цвет + размер)

2. Заказ на эмиссию КМ (POST операция EMISSION)
   → Teksher генерирует N КИЗ кодов, списывает деньги
   → коды в статусе ISSUED

3. Печать стикеров с DataMatrix кодом
   → распечатать каждый код → наклеить на единицу товара

4. Регистрация Нанесения (POST операция MARKING)
   → Teksher переводит коды ISSUED → APPLIED

5. Регистрация трансграничной отгрузки (Трансгран)
   → при отправке партии в Россию

6. Продажа в РФ — сканирование при продаже
   → Честный Знак РФ: APPLIED → SOLD
```

#### Для интеграции ELESTET (этап Маркировка в фулфилменте)
```
1. GET /facade/api/v1/products?... → найти GTIN по артикулу
2. GET /facade/api/v1/marking_codes/filter?gtin=...&status=ISSUED → получить доступные КИЗ
3. Распечатать стикеры (наш модуль стикеров уже умеет DataMatrix)
4. POST операция MARKING → подтвердить нанесение в Teksher
```

```css
@media (pointer: coarse) {

}
```

- **WB Feedbacks API**: `GET /api/v1/feedbacks` — заголовки rate-limit всегда null, поэтому используется exponential backoff
- **Шаблоны**: CRUD в таблице `review_templates`; приоритет: ключевые слова → оценка → универсальный; флаг `is_auto`
- **matchTemplate / applyTemplate**: подстановка `{buyer_name}`, `{product_name}`, `{stars}`
- **Ручные ответы**: textarea + chips шаблонов по каждому отзыву → PATCH WB API
- **Вкладки**: Без ответа / Отвечено / Шаблоны / 🧪 Тест авто-ответа
- **Вкладка «Тест»** (dry-run): показывает для каждого отзыва из «Без ответа» — какой шаблон совпал (по ключевым словам / оценке / универсальный) и итоговый текст ответа после подстановки переменных. Ничего не отправляется. Итоговая строка: «Будет отвечено: X из Y / Без шаблона: Z»
- **Файлы**: `src/services/reviewsService.ts`, `src/pages/ReviewsPage.tsx`, `supabase/patch_wb_feedbacks.sql`, `supabase/patch_review_templates.sql`

# Утверждённая модель стадий партии и межстадийной приёмки (31.08.2026)

## Термины и иерархия
- **Партия** — единый объект на всём пути работ.
- **Стадия** — участок работы одной компании-исполнителя.
- **Этап** — операция внутри стадии: Приёмка, ОТК, Упаковка, Маркировка, Короба, Логистика.
- При включённом pipeline партия получает несколько последовательных стадий; у каждой стадии собственный исполнитель и набор этапов.
- Без pipeline партия логически имеет одну стадию своей компании, но существующий интерфейс и рабочий процесс не меняются.
- Партия с pipeline не удаляется. Завершённые партии скрываются только существующей сортировкой/фильтрацией.

## Передача между стадиями
- Партия передаётся строго целиком и только следующей стадии настроенного snapshot-пайплайна. Частичной передачи и возврата нет.
- После отдельного действия «Завершить стадию» следующая стадия автоматически активируется.
- Для следующей стадии `Заявлено` формируется только из актуального количества **годного** товара предыдущей стадии.
- У следующей стадии есть собственная фактическая приёмка. Кнопка «Принять всё» переносит заявленное в годное фактически принятое и ставит брак `0`.
- Фактически получено стадией = `годное + брак`. Не приехавший товар в складской остаток не входит.
- Межстадийное расхождение предыдущая стадия видит только после фактической приёмки следующей стадии: `передано годного - (принято годного + принято брака)`.
- Следующая стадия не получает отдельного предупреждения о предыдущей: её источник уже виден в `Заявлено`.
- Расхождение нельзя скрыть или закрыть отметкой «Просмотрено»; оно исчезает только после совпадения актуальных данных через корректировку.

## Корректировки и история
- Обычные записи можно менять до завершения. После завершения изменение выполняется только отдельной корректировкой исполнителя этой стадии.
- Владелец партии не корректирует данные стадии партнёра.
- Корректировать можно количество годного/брака, добавление или исключение товара, данные товара, короба и склад.
- Старые значения не удаляются: история `Заявлено`, фактической приёмки, склада и остальных изменённых данных остаётся в журнале.
- Если предыдущая стадия после передачи корректирует годное количество, актуальное `Заявлено` следующей стадии обновляется с сохранением прежнего заявленного значения в истории. Фактическая приёмка следующей стадии автоматически не меняется.
- Тарифы не являются корректировкой партии: каждая компания применяет собственные действующие тарифы и расходники для выставления счёта заказчику.

## Остатки
- Без pipeline остаток появляется только после завершения партии.
- С pipeline остаток компании формируется только после завершения её стадии.
- При передаче годный товар списывается из активного остатка отправителя и до завершения следующей стадии находится в состоянии передачи/обработки, не входя в активный остаток компаний.
- Брак остаётся на складе компании, которая его обнаружила. Возврат в предыдущую компанию и ликвидация брака будут проектироваться отдельно, не в текущей задаче.
- Последняя стадия и партия без pipeline сохраняют на своём складе всё фактически принятое: годное и брак.

## Поставки, короба и QR
- Поставка и короб продолжают принадлежать одной общей партии; существующий системный QR сохраняется при передаче.
- Новые поставки используют сквозной актуальный счётчик компании-владельца партии, а не номер, следующий за переданной поставкой. Номер резервируется атомарно в БД с учётом поставок, созданных владельцем параллельно.
- Новые короба получают уникальные номера из актуального счётчика своей поставки; старые короба и QR остаются в истории предыдущей стадии.
- Исполнитель стадии хранится в данных стадии и не меняет корневую системную идентичность партии в QR.

## Ограничения реализации
- Не менять существующие размеры, типографику, скроллы, анимации и несвязанный UI.
- Существующие партии и данные мигрируются безопасно: старое `qty_received` считается годным, брак по умолчанию `0`.
- Все серверные изменения количества, истории, остатков и переходов должны быть атомарными и проверяться в БД, а не только в интерфейсе.

- Тарифы, расходники, исполнители и журнал работ принадлежат компании-исполнителю стадии.
- Отдельных действий «зафиксировать годное» и «зафиксировать брак» не должно быть. Единственная точка фиксации результата — существующее завершение этапа.
- Завершение этапа атомарно сохраняет его годный результат и выявленный брак, создаёт исторический снимок и передаёт следующему включённому этапу только годное количество.
- Привязка брака к товару должна происходить в обычной строке/форме ввода этапа, без отдельной кнопки.

## HANDOFF 31.08.2026 — стадии, приёмка и качество (полный контекст сессии)

### Утверждённая предметная модель

- Иерархия: `Партия → стадии компаний → этапы каждой стадии`.
- Если пайплайн не включён, партия имеет одну обычную стадию и сохраняет действующее legacy-поведение.
- Если пайплайн включён, список стадий является snapshot настроенного пайплайна на момент создания партии. Передача идёт только целиком и строго следующему исполнителю; частичных передач стадий нет.
- В каждой стадии есть собственные `Заявлено` и `Принято фактически`. Предыдущая завершённая стадия автоматически формирует `Заявлено` следующей только из своего годного выхода.
- Следующая компания независимо выполняет фактическую приёмку. Кнопка `Принять всё` одним действием копирует её заявленные значения в фактические.
- Корректировка предыдущей стадии обновляет только актуальное `Заявлено` следующей стадии. Уже выполненная фактическая приёмка другой компании автоматически не перезаписывается.
- Предыдущая стадия не показывает расхождение с предыдущей компанией. Она показывает только собственное расхождение со следующей стадией, когда следующая уже внесла фактическую приёмку. Расхождение нельзя скрыть как «просмотренное» — оно существует, пока количества действительно не сопоставлены.
- Завершённые значения не удаляются. Корректировка создаёт новое актуальное состояние, а старое остаётся в истории как изменённое/скорректированное.
- Возврата стадии нет. Есть корректировки, которые последовательно обновляют заявленные значения дальнейших стадий, но не меняют чужую фактическую приёмку.
- Pipeline-партии нельзя удалять или архивировать. Для незасорённого списка используется уже существующая фильтрация по статусу.

### Поток качества внутри одной стадии

- `Заявлено` нигде не является базой последующих этапов.
- Фактическая приёмка хранит отдельно годное и брак. ОТК получает только годное фактической приёмки.
- Каждый следующий включённый этап получает только годный выход предыдущего включённого этапа: `приёмка → ОТК → упаковка → маркировка → короба → логистика`, пропуская отключённые этапы.
- ОТК — основной этап выявления брака, но брак может обнаружиться и на остальных этапах.
- Брак не передаётся дальше. Он накапливается с указанием этапа, причины/контекста, автора, времени и истории изменения.
- Годное количество каждого этапа является результатом/фактом обработки этого этапа.
- Никаких отдельных кнопок `Зафиксировать годное` или `Зафиксировать брак` не добавлять. Существующее действие `Завершить этап` само атомарно фиксирует годный результат, брак и исторический снимок, после чего передаёт дальше только годное.
- Вопрос о новом вводе брака на этапах `Короба` и `Логистика`, а также о точной товарной привязке общего брака ОТК/упаковки намеренно отложен пользователем: **пока не реализовывать**.

### Завершение стадии и остатки

- Отдельная кнопка завершает стадию (для обычной партии — завершает единственную стадию/партию) и передаёт годное следующей стадии.
- Складской остаток компании появляется только после завершения её стадии; у обычной партии — после завершения всей партии.
- На собственном складе завершившей стадии учитывается всё фактически принятое ею, включая обнаруженный брак. На следующую стадию уходит только годное после последнего включённого этапа.
- Промежуточное годное после передачи остаётся только историей (`transferred`), а не активным остатком передавшей компании. Брак остаётся активным остатком обнаружившей компании. Способ возврата/ликвидации брака будет спроектирован позже.

### Владение данными компаний

- Владелец корневой партии остаётся владельцем партии, поставок, сквозных номеров поставок, коробов и системных QR коробов на всех стадиях.
- Исполнитель стадии может выполнять разрешённые операции своей стадии, но не получает поставки/короба в собственное пространство системной нумерации.
- Тарифы, расходники, сотрудники и записи выполненных работ принадлежат компании-исполнителю стадии и используются для её собственного расчёта услуг.
- Склад, указанный в данных стадии, является корректируемым операционным значением; изменение склада должно попадать в историю корректировки.

### QR и готовые короба

- Системная колонка `ШК короба` остаётся обязательной и не отключается в настройке Excel.
- Основной шаблон готовых коробов: `Баркод товара`, `Кол-во товаров`, `ШК короба`, `Срок годности`, `Номер короба`; дополнительные товарные колонки выбираются как раньше.

- Идея дополнительных ШК и выбора, какой ШК печатать, полностью отменена пользователем. Существующие кнопки печати QR не расширять этой логикой.
- Импорт готовых коробов должен создавать поставку/короба и заранее раскладывать товары по нужным коробам. Приёмка берёт из импортированных коробов количество коробов и единиц, не перезаписывая лишние товарные поля.

## 2026-08-31 — Склад приёмки, корректировки и просмотр складских остатков

- У каждой pipeline-стадии один физический WMS-склад исполнителя; у обычной legacy-партии — один физический WMS-склад компании партии. Это `wms_warehouses`, а не склад назначения WB из `warehouses` и не поле `notes` товара.
- Склад выбирается в строке способов приёмки сразу после переключателей, с отдельным промежутком и без выравнивания к правому краю. Стили существующих переключателей не объединяются и не меняются.
- Склад разрешено выбрать до или после добавления товаров, но завершить внутренний этап `Приёмка` без склада нельзя.
- До завершения внутренней `Приёмки` склад и строки приёмки свободно добавляются, изменяются и удаляются как обычные рабочие данные. Это не корректировка.
- После завершения внутренней `Приёмки` те же данные доступны только через явный режим `Корректировать`: склад, добавление новой строки, исключение строки, баркод, название, артикул, цвет, размер, заявленное/годное/брак и количество готовых коробов.
- После завершения приёмки товарная строка физически не удаляется: используется `is_excluded`, а изменения пишутся в append-only историю с признаком `is_correction`. Изменение склада также получает отдельную историю.
- Завершение внутренней `Приёмки` не завершает pipeline-стадию и ничего не передаёт следующей компании. Межстадийная передача и создание складского остатка выполняются только отдельным `Завершить стадию`; у legacy-партии — завершением всей партии.
- На странице `Склад` у строки склада добавлена кнопка товаров непосредственно слева от редактирования. Она показывает текущие активные остатки завершённых стадий/партий: юридическое название магазина первым, рабочее вторым, товарные реквизиты, партию/стадию, годное/брак и количество.
- Серверный патч: `supabase/patch_fulfillment_wms_warehouse.sql`. Он добавляет WMS-склад к стадии/legacy-партии/остатку, аудит склада, признак корректировки истории приёмки, ограничения после завершения приёмки и RPC `get_wms_warehouse_products`.
- Безопасный backfill назначает склад только там, где у исполнителя ровно один WMS-склад. Неоднозначные старые записи остаются без назначения и требуют ручной корректировки.
